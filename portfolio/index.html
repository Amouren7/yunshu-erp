项目定位

不是页面拼装，而是一条能对账的业务链

经典 ERP 的难点不在表单，而在单据之间的数量、成本与凭证必须始终一致。这个项目的目标，是用一套可维护的引擎把这条链跑通。

问题：销售发货后，库存、应收、成本、总账、来源单状态五处都要变。任何一处遗漏，月底就对不上账。

做法：所有业务动作收敛到 12 种单据和一套状态机，审核动作在同一个数据库事务里完成过账，失败整体回滚。

结果：库存台账只增不改，凭证借贷必平，应收应付与发票、收付款可逐笔核对，报表数据来自同一份账。

验证：端到端接口、边界权限、全站页面与真实浏览器流程都有脚本覆盖，交付后仍可持续回归。

核心机制

四个决定系统能否长期维护的设计

01

元数据驱动单据引擎

12 种单据共用 documents、document_lines、document_logs 三张表。字段、状态机、动作、转单规则集中在 docTypes.mjs，前端由 /api/meta 动态渲染，新增单据类型不建表、不写表单。

02

审核即过账，事务内闭环

发货审核同时扣减库存、确认收入与应收、结转销售成本、生成会计凭证、回写来源单已发数量。任一步失败，整笔业务回滚，不会留下半成品数据。

03

移动加权平均成本

入库按数量与金额重算均价，出库取当前均价计价，每笔出入库写入不可变库存台账。库存金额、销售成本与总账存货科目来自同一套计算。

04

权限落到数据行

RBAC 以模块乘动作授权，叠加 data_scope 的本人、本部门、全部三级范围。列表自动过滤，详情、编辑、审核在服务端做越权拦截，前端菜单与按钮同步隐藏。

系统架构

单体部署，边界清楚

一个 Node 进程同时提供 API 与前端静态资源，业务逻辑按领域拆在 lib 层，数据落地 SQLite。部署只需要 Node 22.5 以上，没有外部服务依赖。

前端与 API 同进程部署；领域逻辑位于 server/lib，接口位于 server/api，启动时自动挂载。

边界与取舍

能做什么，不能做什么

把限制写在作品集里，比藏在演示里更可信。

适合的场景

  • ERP 业务流程学习与教学演示
  • 中小企业内部试点的功能原型
  • 全栈项目作品展示与面试讲解
  • 二次开发起点：单据、科目、编号都可配置

暂不覆盖

  • 固定资产、预算、委外、质检、多币种、银行对账
  • 多级审批流与金额阈值，当前为单据级审批
  • 高并发场景：单进程 SQLite，适合小团队
  • 商用安全加固：默认密码、HTTPS、限流需自行配置

所有客户、供应商、物料与单据均为模拟数据；项目在 AI 辅助下完成编码，需求拆解、架构、数据模型、验收与缺陷修复由我负责。

Project in English

Yunshu ERP is a full-stack ERP built for small manufacturers. Eleven modules share one metadata-driven document engine: approving a document posts inventory, receivables or payables, cost of goods and double-entry vouchers inside a single transaction. The stack is Node.js with built-in SQLite, React 18, TypeScript and Ant Design, deployed as one process. Forty-three tables, 138 REST endpoints, and automated e2e, boundary and browser tests back the build.
